# Publication and privacy audit — November 2026

## Scope and findings

The repository was already public when this audit began. The audit covered the
current tracked source, reachable Git history, commit attribution, and the prior
release's text files, native binaries, and NuGet package members.

- Gitleaks 8.30.1 scanned all 11 baseline commits and reported no credentials.
- A separate review covered 107 historical text blobs for contact addresses,
  personal home paths, and internal domains. Matches were the intentional
  invalid-URL fixture and GitHub noreply attribution.
- Release files were checksum-verified before inspection. Fifteen release assets
  or package members were reviewed. Email-shaped strings in Native AOT images
  were .NET symbol names, not private contact addresses.
- Current examples were generalized and the repository documentation now reflects
  public availability. No personal machine configuration or private contact data
  was identified.

Public copyright/author names, the GitHub repository identity, and GitHub noreply
commit identities remain intentional attribution. Historical public package
examples remain in old revisions. No history rewriting was performed.

GitHub's managed secret-scanning enablement API reported that the feature was
unavailable for this repository. The independent Gitleaks history scan and the
tracked-file privacy check are therefore explicit CI/release gates.

## Enforced publication controls

- Owner-controlled updates to `main` and creation/update/deletion of `v*` tags.
- `release` and `nuget-publish` environments accept only `v*` tags, with no branch
  rules. These protections are configured on GitHub, outside modifiable PR YAML.
- The NuGet policy requires `nuget-publish` in addition to the canonical repository
  identity and `release.yml` workflow. A broader duplicate policy would weaken this
  boundary and should not be retained.
- Only the NuGet job has `id-token: write`; build/test jobs are read-only and do
  not persist checkout credentials.
- Release tags must match the project version and point to a commit already on
  `main`. Artifacts must come from the same verified run.
- NuGet package ID, version, digest, and size are verified before credential
  issuance. New GitHub releases are immutable.

## Executed negative controls

- Twelve rejected context cases cover forks, wrong immutable IDs, PR events,
  branch dispatches, malformed tags, and version mismatch.
- [Release dispatch on main](https://github.com/MoaidHathot/MHX/actions/runs/45495752162)
  skipped all publishing jobs.
- [Tag-only environment probe](https://github.com/MoaidHathot/MHX/actions/runs/45495751046)
  was rejected by GitHub because `main` cannot deploy to `nuget-publish`. No runner
  step executed. Failure is the expected result of this negative-control workflow.

## Publication evidence

[Release run 45496372993](https://github.com/MoaidHathot/MHX/actions/runs/45496372993)
passed the Windows/Linux/macOS build and security gates, published immutable
`v0.2.3`, obtained the short-lived NuGet credential, and received NuGet's HTTP 201
response followed by **Your package was pushed** for `MHX.0.2.3.nupkg`.

After indexing, NuGet.org's public v2 metadata returned `MHX` version `0.2.3`.
An isolated `dotnet tool install` downloaded that version directly from NuGet.org's
v2 feed, and the installed executable reported `0.2.3`.

Administrators of the GitHub/NuGet accounts
remain trusted and can change security settings. These controls isolate untrusted
contributors; they do not claim protection against account-administrator compromise
or every possible class of sensitive information.
